---
name: add-pgmem-extension
description: Add (bundle) a PostgreSQL contrib extension to pgmem, or check which ones can be. Edits wasm/build.sh, vendors the upstream regression tests, rebuilds the wasm module and the generated Go backend, smoke-tests CREATE EXTENSION and replays the regression suite. Use when asked to add, bundle, enable, link or support an extension in pgmem, or when CREATE EXTENSION says an extension is not available.
---

pgmem links PostgreSQL extensions statically into its wasm module, so
adding one means rebuilding that module and the Go code generated from
it. The driver `skills/add-pgmem-extension/add-extension.sh` does the
mechanical parts; this file is its manual. All paths are relative to
the repository root, and the driver can be run from any directory in it.

Two audiences: maintainers bundling one more extension into pgmem
itself, and people building a custom pgmem with an extension the
release does not ship. The steps are the same; a custom build simply
is not sent upstream.

## Prerequisites

Go (go.mod's version), python3, curl and either Devbox or Emscripten.
The committed generated code follows Devbox's Emscripten 6.0.8, so use
Devbox unless you know why not (macOS/Linux):

```bash
curl -fsSL https://get.jetify.com/devbox | bash   # once, if `devbox` is missing
devbox install                                    # emscripten, binaryen, bison, flex, make
```

The AOT step runs natively (git does not work inside Devbox, see
Gotchas) and needs git, go, python3 and `wasm-opt`; the driver takes
`wasm-opt` from `PATH` (`brew install binaryen` / `apt-get install
binaryen`) or, failing that, from the Devbox profile.

## Run (agent path)

1. See what is bundled and what upstream contrib modules still carry
   regression tests:

   ```bash
   ./skills/add-pgmem-extension/add-extension.sh status
   ```

   The first call downloads the pinned PostgreSQL source (the PGlite
   fork, ~40 MB) into `wasm/out/src`, verified against
   `wasm/postgres-pglite.lock`.

2. Add one (contrib name as in `contrib/<name>`; `pg_surgery` below is
   the module this skill was verified with, then dropped again because
   it fails the selection rule in `.knowledge/policy/bundled-extensions.md`):

   ```bash
   ./skills/add-pgmem-extension/add-extension.sh add pg_surgery
   ```

   This appends the name to `CONTRIB_MODULES` in `wasm/build.sh`,
   copies `contrib/<name>/{sql,expected,data}` to
   `testdata/regress/<name>`, and adds the Makefile's `REGRESS` list to
   `contribRegress` in `regress_test.go`. It then prints what it could
   not do for you:

   - `!! meta-commands the regress runner does not emulate` lists
     psql commands (`\d`, `\df`, `\bind`, ...) found in the vendored
     `.sql` files. The runner only knows `\set \unset \gset \if \elif
     \else \endif \echo \x \copy \q`. Cut those lines from both the
     `.sql` and the `.out` (see the comments in `contribRegress` for
     files trimmed that way), or drop the file from the list.
   - `!! REGRESS_OPTS` means the upstream suite needs server settings
     (`--temp-config`) or a preloaded extension (`--load-extension`);
     mirror them in `regressSuites` in `regress_test.go` as
     `pg_stat_statements` and `vector` do.
   - `note: SHLIB_LINK` means the module links a host library. wasm
     has none; `uuid-ossp` in `wasm/build.sh` (`MODULE_CFLAGS_*`,
     `MODULE_EXTRA_OBJS_*`, `wasm/pgmem_uuid.c`) shows how a slice of
     one is supplied instead.

3. Edit the four extension lists by hand: the `- Extensions:` line in
   `README.md`, `.knowledge/policy/bundled-extensions.md`, and the
   tables in `website/src/content/docs/extensions.md` and
   `website/src/content/docs/ja/extensions.md`.

4. Rebuild. This is the slow part (numbers from an M-series Mac with
   `JOBS=8`, the default):

   ```bash
   ./skills/add-pgmem-extension/add-extension.sh build
   ```

   | step | what it writes | time |
   |---|---|---|
   | `wasm/build.sh` | `wasm/out/postgres.wasm`, `internal/assets/share.tar.gz` | 4 min 47 s (a from-scratch configure and compile; a warm `wasm/out` is faster) |
   | `wasm/gen-aot.sh` | `internal/aot/pgaot/**` (Go generated by the pinned wasm2go fork, cloned and built into `toolchain/` on first use) | 1 min 15 s |

   `build` is `wasm` then `aot`; each is also a subcommand of its own,
   so a failed AOT step does not cost another wasm build. `wasm` goes
   through `devbox run` when `emcc` is not on `PATH`; `aot` always runs
   natively (see Gotchas) and takes `wasm-opt` from `PATH`, or from the
   Devbox profile when the host has none. `internal/pgdata` (the initdb
   image) does not change: initdb only installs plpgsql, so
   `pgmem-mkdata` is not part of this.

5. Smoke test: start pgmem, `CREATE EXTENSION`, list what it installed.

   ```bash
   ./skills/add-pgmem-extension/add-extension.sh smoke pg_surgery
   ```

   Before the rebuild this fails with `extension "pg_surgery" is not
   available`; after it, it prints the version and the objects. The
   first Go build after `gen-aot.sh` compiles 115 MB of generated Go
   (about a minute); later runs are cached.

6. Replay the upstream regression files against pgmem:

   ```bash
   ./skills/add-pgmem-extension/add-extension.sh test pg_surgery
   ```

   A failure prints a diff of the psql-style transcript against
   `testdata/regress/<name>/expected/<file>.out`. To tell a pgmem bug
   from a harness bug, replay the same files against a real server:
   `REGRESS_DSN=postgres://... go test . -run TestContribRegress/<name>`.

7. Commit everything as one commit, `pgmem: bundle <name>`. The diff is
   large but mostly generated: the extension's functions land in
   `internal/aot/pgaot/p*/` in files named after their subject
   (`heap.go` for pg_surgery's `heap_force_*`; `seg.go` for seg), and
   every file that carries a static-data address shifts (that is
   inherent to appending a module's rodata).

## Extension outside the PostgreSQL tree

pgvector is the template. It has no driver support; copy its pattern:

- `wasm/pgvector.lock`: `version`, `url`, `sha256`.
- `wasm/build.sh`, the block starting at `# pgvector: not in the
  PostgreSQL tree`: fetch and verify the archive, compile each `.c`
  with `$PG_CFLAGS` against `$PREFIX/include/postgresql/server`,
  with `-DPg_magic_func=Pg_magic_func_<name> -D_PG_init=_PG_init_<name>`
  (every module is renamed this way so they can share one static
  link), append `<name>=<objs>` to `GEN_ARGS` and the objects to
  `MODULE_OBJS`, and copy `<name>.control` plus the SQL scripts into
  `$PREFIX/share/postgresql/extension/`.
- Its tests: `testdata/regress/vector` and the `"vector"` entries in
  `contribRegress` and `regressSuites`.

Then steps 3 to 7 above.

## Test

The whole suite, extensions included (about 10 s once the generated Go
is compiled):

```bash
go test . -run TestContribRegress -count=1
```

## Gotchas

- **`gen-aot.sh` cannot run inside Devbox.** It clones the wasm2go fork
  with git, and in the Devbox environment git fails with
  `error: tool 'git' not found` (the macOS git shim cannot find a
  developer directory there). The driver therefore runs the AOT step
  natively with the host's git, go, python3 and `wasm-opt`.
- **A copied `wasm/out` rebuilds from configure.** `wasm/out/configure.sig`
  embeds the checkout path, so a build tree copied from another checkout
  or worktree reconfigures and recompiles everything (the 4 min 47 s
  above). Not an error; do not interrupt it.
- **The regression diff can be the harness, not pgmem.** The psql
  emulation in `regress_test.go` is small: a fixed set of meta-commands
  and its own aligned-output formatter. `pg_surgery`'s `heap_surgery`
  failed only because the formatter did not right-align `xid` columns
  the way psql does (fixed in `rightAligned` while writing this skill).
  When the mismatch is whitespace, alignment or a `\` command, fix the
  harness; `REGRESS_DSN` against a real server settles which side is wrong.
- **The generated diff is large and mostly renumbering.** Functions with
  a symbol name keep their file (`p*/heap.go`, ...); the unnamed ones in
  `p*/fn.go` are numbered in module order and shift when a module is
  inserted, and every static-data address moves. Review the hand-written
  files and the new module's own functions, not the churn.
- **The smoke and test commands compile 115 MB of generated Go.** The
  first `go` invocation after `gen-aot.sh` takes about a minute (the
  `test` subcommand showed 25 s wall on a warm cache, 51 s cold); after
  that they run in a few seconds.
- **`add` is idempotent.** Running it twice for the same name says so
  and changes nothing, so it is safe to re-run after fixing something
  by hand.

## Troubleshooting

- **`error: tool 'git' not found` from `devbox run -- ./wasm/gen-aot.sh`**:
  git does not work inside Devbox; run `add-extension.sh aot` (native).
- **`extension "<name>" is not available` from `smoke`**: the share tree
  does not have the control file yet, that is, `build` has not run since
  `add`, or the Go build is still the old one.
- **`output differs from expected` in `test`**, with the actual transcript
  saved to `$TMPDIR/pgmem-regress-<name>-<file>.out`: diff it against
  `testdata/regress/<name>/expected/<file>.out`. Alignment or a
  meta-command means the harness (see Gotchas); an ERROR line means
  pgmem.
- **`regress: unsupported meta-command \d...` panic**: a psql command
  the runner does not emulate slipped through; cut it from the `.sql`
  and `.out`, as the comments above `contribRegress` describe for other
  suites.
