## Test an application-managed repository with one annotation

If Spring Boot or Micronaut normally creates the repository and its DataSource, use the framework's `@ShadowPg`. These examples assume `OrderRepository` is registered as an application bean. The test retrieves that same bean. The application needs no pgmem-specific changes. Put `db/schema.sql` in `src/test/resources`, or omit `schema` when the application runs its own startup migration. Add `seed = "db/seed.sql"` for initial rows. Each method starts from the same prepared data.

<Tabs syncKey="java-unit-framework">
<TabItem label="Spring Boot">

```java
@ShadowPg(schema = "db/schema.sql")
class OrderRepositoryTest {
    @Autowired OrderRepository orders;

    @Test void createsAndFindsAnOrder() throws SQLException {
        Order created = orders.create("book");
        assertEquals(created, orders.findById(created.id()));
    }
}
```

Add `testImplementation("io.github.shibukawa.pgmem:pgmem-spring:1.18.0")` and import `io.github.shibukawa.pgmem.spring.ShadowPg`. This annotation also starts a random-port HTTP server for API tests.

</TabItem>
<TabItem label="Micronaut">

```java
@ShadowPg(schema = "db/schema.sql")
class OrderRepositoryTest {
    @Inject OrderRepository orders;

    @Test void createsAndFindsAnOrder() throws SQLException {
        Order created = orders.create("book");
        assertEquals(created, orders.findById(created.id()));
    }
}
```

Add `testImplementation("io.github.shibukawa.pgmem:pgmem-micronaut:1.18.0")` and import `io.github.shibukawa.pgmem.micronaut.ShadowPg`.

</TabItem>
</Tabs>

Add the PostgreSQL JDBC driver and platform-specific `pgmem-native` dependency from [Java basics](../basics/) for either framework.

## Test a repository through its public methods

`PgmemExtension` prepares the schema once. A `DataSource` parameter receives a fresh fork by default, so a write in one method cannot affect the next. `@PgmemTest(fork = false)` shares a prepared fork for read-only methods. Create the repository with the injected `DataSource`; an existing pool cannot be redirected after construction. In this example, `migrateAndSeed` creates an `orders(id, sku)` table.

<Tabs syncKey="java-unit-example">
<TabItem label="Test">

```java title="OrderRepositoryTest.java"
class OrderRepositoryTest {
    @RegisterExtension
    static PgmemExtension pg = PgmemExtension.builder()
            .database("app")
            .prepare(t -> migrateAndSeed(t.jdbcUrl()))
            .build();

    @Test void createsAndFindsAnOrder(DataSource ds) throws SQLException {
        OrderRepository orders = new OrderRepository(ds);
        Order created = orders.create("book");
        assertEquals(created, orders.findById(created.id()));
    }

    @Test @PgmemTest(fork = false)
    void missingOrderReturnsNull(DataSource ds) throws SQLException {
        assertNull(new OrderRepository(ds).findById(-1));
    }
}
```

</TabItem>
<TabItem label="OrderRepository">

```java title="OrderRepository.java"
record Order(long id, String sku) {}

final class OrderRepository {
    private final DataSource db;
    OrderRepository(DataSource db) { this.db = db; }

    Order create(String sku) throws SQLException {
        try (Connection c = db.getConnection();
             PreparedStatement st = c.prepareStatement(
                     "INSERT INTO orders (sku) VALUES (?) RETURNING id")) {
            st.setString(1, sku);
            try (ResultSet rs = st.executeQuery()) {
                rs.next();
                return new Order(rs.getLong(1), sku);
            }
        }
    }

    Order findById(long id) throws SQLException {
        try (Connection c = db.getConnection();
             PreparedStatement st = c.prepareStatement(
                     "SELECT id, sku FROM orders WHERE id = ?")) {
            st.setLong(1, id);
            try (ResultSet rs = st.executeQuery()) {
                return rs.next() ? new Order(rs.getLong(1), rs.getString(2)) : null;
            }
        }
    }
}
```

</TabItem>
</Tabs>

## Database lifecycle strategies

Start a fresh server when a test needs a different schema. When tests share the same schema and seed data, register one `PgmemExtension` and initialize its template once; then choose a fork scope for each test class.

### A fresh server per test

<Tabs syncKey="jvm-lang">
<TabItem label="Java">

```java
@Test
void schemaVariant() throws Exception {
    try (Pgmem pg = Pgmem.builder().database("app").start();
         Connection conn = DriverManager.getConnection(pg.template().jdbcUrl())) {
        conn.createStatement().execute(SCHEMA_V2);
        // ...
    }
}
```

</TabItem>
<TabItem label="Kotlin">

```kotlin
@Test
fun schemaVariant() {
    Pgmem.builder().database("app").start().use { pg ->
        DriverManager.getConnection(pg.template().jdbcUrl()).use { conn ->
            conn.createStatement().execute(SCHEMA_V2)
        }
    }
}
```

</TabItem>
</Tabs>

### Initialize one template once

Register the extension in a static field. JUnit starts pgmem before the class and calls `prepare` once with the template `Server`; run migrations and seed data there. When `prepare` returns, the extension snapshots that database. The test forks below start from this prepared snapshot, so migrations and seed data stay out of each test method and the test body can focus on its behavior.

<Tabs syncKey="jvm-lang">
<TabItem label="Java">

```java
class OrderRepositoryTest {

    @RegisterExtension
    static PgmemExtension pg = PgmemExtension.builder()
            .database("app")
            .prepare(t -> {
                Flyway.configure().dataSource(t.jdbcUrl(), t.user(), null).load().migrate();
                seed(t.jdbcUrl());
            })
            .build();
}
```

</TabItem>
<TabItem label="Kotlin">

```kotlin
class OrderRepositoryTest {

    companion object {
        @JvmField
        @RegisterExtension
        val pg: PgmemExtension = PgmemExtension.builder()
            .database("app")
            .prepare { t ->
                Flyway.configure().dataSource(t.jdbcUrl(), t.user(), null).load().migrate()
                seed(t.jdbcUrl())
            }
            .build()
    }
}
```

</TabItem>
</Tabs>

Nested classes reuse the outer class's process.

Both scopes below start from this same prepared template. Choose class scope only when every test in the class is read-only; method scope gives each test its own writable copy.

#### Share one fork across a read-only class

Ask for `ForkScope.CLASS` on the parameter, or make it the default with `forkScope(ForkScope.CLASS)` on the builder.

<Tabs syncKey="jvm-lang">
<TabItem label="Java">

```java
@Test
void totals(@PgmemFork(scope = ForkScope.CLASS) DataSource ds) throws Exception {
    try (Connection conn = ds.getConnection();
         ResultSet rs = conn.createStatement().executeQuery("SELECT count(*) FROM orders")) {
        rs.next();
        assertEquals(10_000, rs.getInt(1));
    }
}
```

</TabItem>
<TabItem label="Kotlin">

```kotlin
@Test
fun totals(@PgmemFork(scope = ForkScope.CLASS) ds: DataSource) {
    ds.connection.use { conn ->
        conn.createStatement().executeQuery("SELECT count(*) FROM orders").use { rs ->
            rs.next()
            assertEquals(10_000, rs.getInt(1))
        }
    }
}
```

</TabItem>
</Tabs>

<Aside type="caution">
Every test in the class sees what any of them wrote. Keep writing tests on the default method scope.
</Aside>

#### Fork per method for tests that write

A `Fork`, `DataSource` or `@PgmemFork String` parameter gets a fresh copy of the prepared database, closed after the test. Several parameters in one test share one fork.

<Tabs syncKey="jvm-lang">
<TabItem label="Java">

```java
@Test
void cancelOrder(DataSource ds) throws Exception {
    new OrderRepository(ds).cancel(1);
    try (Connection conn = ds.getConnection();
         ResultSet rs = conn.createStatement().executeQuery("SELECT status FROM orders WHERE id = 1")) {
        rs.next();
        assertEquals("cancelled", rs.getString(1));
    }
}

@Test
void withUrl(@PgmemFork String jdbcUrl) {
    var app = new App(jdbcUrl);
    // ...
}
```

</TabItem>
<TabItem label="Kotlin">

```kotlin
@Test
fun cancelOrder(ds: DataSource) {
    OrderRepository(ds).cancel(1)
    ds.connection.use { conn ->
        conn.createStatement().executeQuery("SELECT status FROM orders WHERE id = 1").use { rs ->
            rs.next()
            assertEquals("cancelled", rs.getString(1))
        }
    }
}
```

</TabItem>
</Tabs>

##### Assert with DbUnit

```java
@Test
void cancelOrder(Fork fork) throws Exception {
    new OrderRepository(fork.dataSource()).cancel(1);

    IDatabaseConnection conn = new DatabaseConnection(DriverManager.getConnection(fork.jdbcUrl()));
    ITable actual = conn.createQueryTable("orders", "SELECT id, status FROM orders ORDER BY id");
    ITable expected = new FlatXmlDataSetBuilder()
            .build(getClass().getResourceAsStream("/after_cancel.xml")).getTable("orders");
    Assertion.assertEquals(expected, actual);
}
```

## Several templates

`template(name, prepare)` adds a second prepared database, and `@PgmemFork("name")` selects it.

```java
@RegisterExtension
static PgmemExtension pg = PgmemExtension.builder()
        .database("app")
        .prepare(t -> migrate(t.jdbcUrl()))
        .template("audit", t -> migrateAudit(t.jdbcUrl()))
        .build();

@Test
void auditTrail(@PgmemFork("audit") DataSource audit) { /* ... */ }
```

## Parallel runs

JUnit's parallel execution works; forks are independent. `maxForks(n)` caps live forks per template (default: a quarter of the server's memory limit divided by a fork's cost, 28 on a 7 GB CI runner). When all slots are occupied, a new fork waits. `forkTimeout(Duration)` makes that wait fail with `pool_timeout`; without it, the wait has no deadline.

```java
import java.time.Duration;

@RegisterExtension
static PgmemExtension pg = PgmemExtension.builder()
        .database("app")
        .maxForks(4)
        .forkTimeout(Duration.ofSeconds(30))
        .build();
```

Every forked test JVM, from Gradle's `maxParallelForks` or Surefire's `forkCount`, starts its own binary and pool. See [limits](../../../limits/) for snapshot, startup and connection-wait timeouts.

<Aside>
Commit or close connections before the snapshot is taken. `prepare` returning with an open transaction makes the snapshot fail with `busy` after 30 seconds.
</Aside>
