PostgreSQL を使うテストスイートに必要なものは三つあります。サーバー、シードデータ入りのスキーマ、そしてテスト同士が互いの書き込みを見ないための仕組みです。よく使われる方法は、どれもどこかで何かを諦めています。

## 既存の選択肢

**Docker と Testcontainers** は公式イメージを動かします。本番と同じビルド、すべての拡張、複数セッションが同時に動く本物のサーバーが手に入ります。その代わり、開発者のマシンと CI ランナーのすべてにデーモンが要ります。初回はイメージを取得し、コンテナの起動には秒単位かかり、macOS や Windows ではメモリを抱えた Linux VM が常駐します。テスト単位の分離は利用者任せです。テンプレートからテストごとにデータベースを作るか、トランザクションをロールバックするかを自分で組みます。

**devbox、nix、組み込み PostgreSQL バイナリ**（zonky embedded-postgres、fergusstrange/embedded-postgres、pytest-postgresql）は、ネイティブの PostgreSQL を動かして Docker を避けます。それでも `initdb` とポストマスターの起動には時間がかかり、データディレクトリはディスクに書かれ、分離はやはりテストごとのデータベースです。

**PGlite** は PostgreSQL を WebAssembly として JavaScript プロセス内で動かします。プロセス内で完結しますが、操作はワイヤプロトコルではなく TypeScript の API 経由です。ORM にはアダプタが要り、接続もひとつだけです。

**SQL エミュレータ**（pg-mem や、PostgreSQL の代わりに使う SQLite）は速い反面、PostgreSQL ではありません。方言、プランナ、拡張の差は本番で初めて表に出ます。

## pgmem の違い

pgmem は同じ PGlite 版の PostgreSQL 18 を使いつつ、Go ライブラリと、ループバックポートでワイヤプロトコルを話す小さな単体バイナリとして配布します。

- **起動はおよそ 0.1 秒。** `initdb` が作ったデータディレクトリを埋め込んであり、メモリに展開するだけだからです。
- **フォークは準備済み状態の複製です。** メモリ上のデータディレクトリを複製し、その上で新しいバックエンドを起動します。マイグレーションとシードはテストごとではなく、スイートごとに一度で済みます。
- **どのドライバでも動きます。** 接続先は普通の `postgres://` や `jdbc:postgresql://` の URL です。
- **各言語で依存はひとつ。** Python の wheel、Maven のアーティファクト、npm パッケージがバイナリを同梱しており、実行時のダウンロードはありません。

## ほかを選ぶべきとき

pgmem は PostgreSQL をシングルユーザーモードで動かします。フォークひとつが 1 セッションで、そこへの接続はトランザクション境界で多重化されます。次のようなテストには Docker か Testcontainers を選んでください。

- 1 つのデータベースに対して本当に同時にセッションを走らせるもの。たとえばロック競合のテスト。
- 同梱していない拡張を使うもの。PostGIS や、pg_cron のようなバックグラウンドワーカー型の拡張など。
- 本番と完全に同じサーバービルドと設定が必要なもの。
