## モデルケース：同じテストスイート、2 つの実行モデル

[`bench/modelcase`](https://github.com/shibukawa/pgmem/tree/main/bench/modelcase)
は小さいけれどごく普通の Go プロジェクトです。ショップのデータ層
（`database/sql`、トリガーとビューを含む 5 本の SQL マイグレーション、
マスタデータとしてカテゴリ 20 件、商品 500 件、ユーザー 1,000 件）と、
それに対する 70 本のテストからなります。テストはケース表で書いてあり、
参照だけのシナリオ 5 つ（ユーザーごとの注文一覧、注文詳細、売れ筋商品、
商品検索、カテゴリ別売上）が各 10 ケースで 50 本、テーブルを更新する
シナリオ 5 つ（注文の作成・キャンセル・出荷、ユーザーと注文の削除、
値引きの適用）が各 4 ケースで 20 本あり、更新後の行を検証します。どのテストも同じ 40 件のサンプル注文から始まります。
テスト関数は両モデルで同一で、背後のフィクスチャだけが違います。

- **pgmem**：`TestMain` がテストプロセス内でサーバーを起動し、スキーマと
  マスタデータを投入してスナップショットを 1 回取ります。参照テストに
  コピーは要りません。スナップショットの後にサンプルデータを 1 回だけ
  投入したテンプレートサーバーをそのまま共用します。更新テストは
  それぞれスナップショットから自分のフォークを作り、サンプルデータを
  投入します。70 本すべてが `t.Parallel()` を呼ぶので、スナップショット
  以降は `-parallel` の枠いっぱいで一斉に走ります。
- **共有サーバー 1 台**：testcontainers-go の PostgreSQL モジュールで起動した
  公式イメージをオンメモリで動かしたもの（PGDATA は tmpfs、`fsync`、
  `synchronous_commit`、`full_page_writes` はオフ、新しいテストプロセスが
  起動する Ryuk も含む）、devbox のネイティブ PostgreSQL 18、公式イメージの `docker run` の
  3 種類です。ドライバがサーバーを起動し、テストバイナリが共有データベースに
  スキーマとマスタデータを投入します。参照テストは共有
  データベース上で並列に走れますが、更新テストはそうはいきません。
  トランザクション系テーブルを TRUNCATE し、在庫と価格を戻し、サンプル
  データを投入してから走り、次の更新テストは順番を待ちます。1 台のサーバー
  で結果を決定的に保つには、こうするしかありません。

バーはそれぞれ実行モデルの 1 ノードで、テストバイナリの中で計っています
（`MODELCASE_TRACE`）。外部サーバーの起動は、app データベースで `SELECT 1`
が通るまでをドライバが計り、テストバイナリの実時間も計ります。合計は起動と
テストバイナリの和で、ノードに含まれない数ミリ秒はバイナリ自身の起動と
終了です。各タイムラインは合計時間が中央値だった実行で、ビルド直後の
初回実行はウォームアップとして記録しません。`go test` の `-parallel` は
既定の `GOMAXPROCS` です。タイムラインはすべて同じ時間軸です。

読み取れること：

- **共有サーバーは更新テストごとに払います。** リセットとサンプルデータ
  投入のコストは、pgmem のフォークとサンプルデータ投入とほぼ同じですが、
  共有サーバーではそれが直列に、フォークでは横に並んで走ります。
- **pgmem の固定費は起動とスナップショットで**、どちらもネイティブ
  サーバーの起動より小さく、コンテナとは比べものになりません。
- **フォークは軽く、重なって進みます。** フォークはデータディレクトリを
  copy-on-write でクローンし（ツリーだけ複製し、ファイルの中身は書き込む
  まで共有）、共有メモリを二重にゼロ埋めしなくなったバックエンドを起動する
  ので、1 つだけなら約 6 ms です。8 つ同時だとページフォルトで競合して
  1 つあたり 10 ms ほどになりますが、20 本のフォークとサンプル投入は
  実時間 120 ms ほどに収まります。
- **共有サーバー上の参照テストはトランザクション境界で直列化されます**
  （pgmem のサーバー 1 つにつきバックエンドセッションは 1 つ）。そのため pgmem
  では、マルチプロセスのサーバーより 1 本ずつは少し遅くなります。どちらに
  しても短い時間です。

```sh
cd bench/modelcase
RUNS=5 ./run.sh                    # pgmem、Testcontainers、devbox、docker
TARGETS="pgmem devbox" ./run.sh    # Docker なし
```

スクリプトはテストバイナリを 1 回コンパイルし、対象ごとにドライバを走らせて
`results/raw.jsonl`（各実行とそのスパン）、`results/summary.json`、そして
このページが描画する `website/src/data/modelcase.json` を書きます。同じ
ディレクトリで `go test ./...` を実行すると、トレースなしの普通のテスト
として pgmem 上でスイートが走ります。

## 最新の AOT 再計測

エクスポートを絞った AOT ビルドで、pgmem ライブラリと単独バイナリの行を
2026-09-18 に再計測しました。起動・メモリなどは各 5 回、Go ベンチマークは
3 回実行しています。darwin/arm64 の strip 済みバイナリは 36.7 MB、zip の
配布物は 16.3 MB、strip 済み Go テストバイナリへリンクした増分は 33.1 MB
でした。Docker、Testcontainers、devbox は再計測せず、比較行は 2026-09-14 の
基準値を残しています。

## 各列が測っているもの

どの計測も、新しいプロセスでサーバーを 1 つ起動し、同じスキーマを流し込んでから測ります。ハーネスは [`bench/alternatives`](https://github.com/shibukawa/pgmem/tree/main/bench/alternatives) にあります。

- **起動〜最初のクエリ**：起動処理を呼び出してから、TCP 経由の `SELECT 1` が成功するまで。`docker pull` と `devbox install` は計測前に実行し、Devbox 環境の解決も計測外の準備で済ませます。`docker run` は新規コンテナと DB クラスタの初期化を含みます。Devbox は初期化済みの永続クラスタと app DB を計測前に準備し、`devbox services up -b` の実行から SQL ready までを計ります。Testcontainers は新しいテストプロセスが起動する Ryuk コンテナも含みます。pgmem バイナリは ready 行が出るまでを計り、Python、Java、Node.js のラッパーはその行を待ちます。
- **テストごとの複製**：準備済みデータベース（ユーザー 1,000 件、注文 10,000 件）の独立した複製を 20 回作り、そのたびに接続して結合クエリを 1 本流したときの中央値です。pgmem はスナップショットからフォークします。docker run と devbox は `CREATE DATABASE … TEMPLATE` と `DROP DATABASE`、Testcontainers は PostgreSQL モジュールの `Snapshot` と `Restore` を使います。後者も内部ではテンプレートデータベースで同じことをしています。
- **インデックス SELECT**：pgx で `SELECT v FROM bench WHERE id = $1` をウォームアップ後に 3,000 回。pgmem の 2 つ目の値は、TCP の代わりにプロセス内ダイヤラ（`Server.Dial`）を使ったものです。
- **20万行ソート**：`SELECT count(*) FROM (SELECT md5(i::text) AS h FROM generate_series(1, 200000) i ORDER BY h) t` を、ウォームアップ 1 回の後に 3 回流した中央値です。
- **メモリ**：負荷中に OrbStack VM がメモリを返すと、コンテナの使用量が多くても Testcontainers の値が `docker run` より小さく見えることがあります。そこでグラフは VM の差分を使わず、DB 側の使用量と計測プロセスの増分を比べます。pgmem はプロセスの `phys_footprint` 増分、バイナリは単独の pgmem プロセスを使います。Docker と Testcontainers は各コンテナの Docker 使用量に Go の計測プロセスの増分を足します。Testcontainers には PostgreSQL と Ryuk が含まれ、メモリ値には `docker stats` の表示を使います（Linux CLI はキャッシュを差し引きます）。devbox は PostgreSQL のポストマスターと子プロセスを合算します。OrbStack VM の差分と絶対値は表に分けて載せています。
- **ダウンロード**：初回に取得するもの。Go ライブラリとしての pgmem は、strip したテストバイナリがリンクによって増える量です。バイナリの行は wheel、jar、npm パッケージが同梱する圧縮済みバイナリの大きさです。イメージは計測したアーキテクチャの圧縮レイヤ、nix closure は devbox が cache.nixos.org から取得する量です。

## 数字の読み方

- **既定値が違います。** サーバーは PostgreSQL の既定値（`shared_buffers=128MB`）を使います。Testcontainers の計測では PostgreSQL 18 のデータディレクトリ（`/var/lib/postgresql/18/docker`）を tmpfs にマウントし、docker run と devbox はディスクを使います。pgmem は `shared_buffers=32MB` でファイルシステムもメモリ上にあるため、一時ファイルにあふれるソートでもディスクに触れません。
- **グラフは DB と計測プロセスのメモリを比べます。** スキーマ準備後とクエリ・分離計測後の中央値および計測回ごとの範囲を示します。Testcontainers は PostgreSQL と Ryuk のコンテナ使用量を含みます。Linux の `docker stats` CLI は表示値からキャッシュを差し引きます。
- **OrbStack VM の差分は別の参考値です。** コンテナの計測ごとに VM を再起動し、アイドル時を記録します。VM は実行中にメモリを解放することがあり、コンテナ使用量が増えても VM の差分が下がる場合があります。表では差分と VM の絶対値を分けています。
- **pgmem のメモリは負荷で増えます。** WebAssembly のリニアメモリはサーバー稼働中は OS に返らず、生きているフォークはそれぞれ自分の複製を持ちます。生きているフォーク 1 つあたりアイドル時の値程度を見込み、`MaxForks` で数を抑えてください。
- **コンテナ方式の差には実行条件も含まれます。** docker run はディスク上に保存しますが、Testcontainers は PGDATA を tmpfs に置き、Ryuk も起動します。そのため、差には保存先と起動方式の違いが含まれます。

## 再現手順

```sh
cd bench/alternatives
RUNS=5 MEM_RUNS=3 ./run.sh
```

OrbStack と devbox が必要です。メモリ計測のパスでは OrbStack を再起動しますが、ほかのコンテナが動いているときは再起動せずに止まります。生の計測値を `results/raw.jsonl`、中央値を `results/summary.json` に書き、要約を `website/src/data/benchmarks.json` にコピーします。このサイトの表はそのファイルを描画しています。
